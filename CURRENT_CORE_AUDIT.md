**Search and data findings**

| File indexing is broad and enabled by default in code. | [default settings](C:/Users/Robert/code/Rust/core/src/settings.rs:98) enables `index_user_files` and clipboard history, despite README language describing file indexing as opt-in. [File discovery](C:/Users/Robert/code/Rust/core/src/file_index.rs:75) recursively builds an in-memory catalog with a 150,000-file cap. | Omit file discovery from v2's first release; make future indexing explicitly opt-in. |

Add a regression case if that feature returns. |
| The search benchmark is stale relative to current types. | [benchmark imports](C:/Users/Robert/code/Rust/core/benches/search_latency.rs:1) reference `destiny`, absent from [the library exports](C:/Users/Robert/code/Rust/core/src/lib.rs:1). | Existing selection work is partly optimized, but still allocates while ranking. | [top-k helper](C:/Users/Robert/code/Rust/core/src/search_text.rs:119) uses partial selection rather than sorting all matches, but collects all scored candidates; comparators request owned tie-break strings. | Cache validity is mostly time-based and state persistence occurs in the interaction path. | [search cache](C:/Users/Robert/code/Rust/core/src/command_router.rs:75) clones a 150 ms cached result; [index replacement](C:/Users/Robert/code/Rust/core/src/command_router.rs:211) does not invalidate it. **Reliability findings relevant to the smaller release**

The [accept-result path](C:/Users/Robert/code/Rust/core/src/ui/launcher/mod.rs:757) records recent usage before attempting execution and has an empty `Err(_)` arm. A failed action can therefore appear as a recent use without an actionable error. Record successful dispatch and surface failures in v2.

The [recent-usage loader](C:/Users/Robert/code/Rust/core/src/recent_usage.rs:153) maps read/parse failures to an empty default store. Its saver and the [settings saver](C:/Users/Robert/code/Rust/core/src/settings.rs:149) write directly to the destination. Distinguish missing/corrupt/unwritable data and use recoverable atomic replacement in the new storage boundary.

**Useful foundations to retain**

The existing project already has typed command/action enums, a [service boundary](C:/Users/Robert/code/Rust/core/src/launcher_services.rs:10), normalized application/file metadata, bounded result limits, domain tests and [original product requirements](C:/Users/Robert/code/Rust/core/docs/requirements.md:1). Reuse suitable behaviour and tests selectively. The main opportunity is to reduce scope and enforce those boundaries at runtime; wholesale replacement of every algorithm is unnecessary.

The old requirements contain historical platform/dependency notes. Current upstream [GPUI documentation](https://github.com/zed-industries/zed/blob/main/crates/gpui/README.md) describes a Windows backend. Framework selection in the v2 plan is therefore a measurement decision, not a conclusion that GPUI cannot run on Windows.
